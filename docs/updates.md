# 自动更新与发布

【用户已确认】软件支持自动更新，文档同步维护。产品行为见[产品规范](product.md#9-013-软件更新)，内部设计见[技术设计](technical-design.md#9-013-自动更新架构)，实际证据见[验收记录](acceptance.md#9-013-自动更新验收)。

## 用户如何更新

【方案默认值】0.1.2 及更早版本需先手动安装一次 0.1.3。之后 Windows 安装版启动 30 秒后及每 6 小时检查正式新版本，发现后后台下载。设置页可关闭自动检查，或随时手动检查和重试。

【方案默认值】下载校验完成后显示“重启并更新”。点击并确认后，当前学习保存为暂停，然后安装并重启；记录和计划保留。学习中不自动重启，关闭到托盘和彻底退出也不自动安装。未安装目录、开发版及测试模式明确禁用生产更新。

【方案默认值】关闭自动开关只停止之后的定时检查，不终止正在进行的下载。检查失败或下载损坏时可重试，学习功能继续；准备好的更新保留在更新器缓存中。电脑须能访问 GitHub 及其 Release 下载域名；没有设置代理或第三方镜像。

## 发布者操作

【方案默认值】源码提交到 main 与软件正式发布分开。普通源码提交不会触发客户端更新。每次正式发布必须提高 package.json 和锁文件的版本，更新设置页版本后备文本与 docs，并新增 docs/releases/版本.md。保持 appId、产品名和用户数据目录稳定。

【方案默认值】`.github/workflows/release.yml` 支持三种触发方式：推送 v* 标签、创建 release/v版本 分支，或从 GitHub Actions 的 Windows release 页面选择 Run workflow。分支用于现有连接器也能发起发布；标签与分支名须与 package.json 版本相符。没有任何发布令牌写入源码。

【方案默认值】发布任务在 Windows 上运行 npm ci、核心测试、NSIS 打包、打包应用桌面测试、真实更新下载测试，全部通过才运行 scripts/publish-release.mjs。构建命令明确 --publish never，本机打包不会意外发布。发布步骤用仓库临时 GitHub Token 和 GitHub CLI，无需让使用者配置 Token。

【方案默认值】发布脚本检查包版本和安装包 SHA-512 与 latest.yml 一致，再创建草稿 Release，上传安装包、blockmap、latest.yml 与 SHA256SUMS.txt，最后公开。草稿期间客户端不可见，避免提前发现未上传完整的版本。脚本拒绝覆盖已公开版本；草稿失败可在确认原因后重试。安装包不提交到 Git 源码历史。

【方案默认值】首次接入后，必须实际运行一次上述流程并确认 Release 资产可访问，才可认为更新源已开通。GitHub App 需要具备工作流文件写入权限，Actions 需要允许执行及任务级 contents:write；若连接器或仓库限制阻止，应明确记录实际失败原因，不能声称发布成功。

## 失败与回滚

【方案默认值】客户端下载损坏会拒绝就绪/安装，允许重新检查下载。安装前保存失败会保留应用运行，不开始安装。安装器启动失败会显示错误；安装器运行后的系统故障不由状态机保证自动恢复，需人工验收。

【方案默认值】不允许自动降级，不提供旧版本覆盖同一版本号的回滚。若正式版本有问题，修复后提高版本号并重新发布。用户数据保持 schemaVersion 1；未来迁移前需备份并单独验证。不要删除或覆盖用户学习文件来解决更新问题。

【方案默认值】当前个人试用版本尚无 Authenticode 代码签名证书，依靠 GitHub HTTPS 和安装包 SHA-512 校验，不宣称具备发行者签名。签名证书、首次真实升级、安装权限及长期试用的状态以[验收记录](acceptance.md)为准。
